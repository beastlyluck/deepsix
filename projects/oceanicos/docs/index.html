OceanicOS

A digital twin of an automated container terminal: six ship-to-shore cranes on two berths, 32 yard blocks, 16 AGVs, a gate. The twin runs the terminal forward as a discrete-event simulation, and the product is the dispatcher that sits inside it: an assignment matrix that pairs AGVs to boxes and boxes to blocks using a spatio-temporal traffic forecast and a per-line dwell model.

Physical assetContainer terminal: 2 berths × 3 STS cranes, 4×8 yard blocks (320 TEU each), 16 AGVs, single truck gate
Final productterminal.policy.Matrix: Hungarian pairing + block scoring; api.server: REST plan endpoints and WebSocket replay
Bottlenecks addressedSpatio-temporal graph model for AGV lane density; hierarchical volume forecast that must add up across terminal → line → service
StackPython stdlib heap DES, NetworkX road graph, SciPy Hungarian, LightGBM/sklearn readout, NumPy Holt-Winters + MinT, DuckDB/SQLite event store, FastAPI + WebSocket, canvas dashboard
Runtime48 h simulated under two policies, model fits and forecasts: ~1 min on a laptop CPU
Everything is synthetic. The vessel schedule, dwell distributions and layout are invented; the claims are about the method under controlled comparison, not about a real port.

3. Terminal graph

The yard is a 4×8 grid of 120×60 m blocks with 30 m AGV lanes between them; the quay runs along y=0 with cranes at 170 m pitch. Lane intersections are graph nodes, lanes are edges weighted by metres. Each crane, block and the gate hangs off its nearest intersection. Travel time is path length at 5 m/s plus 12 s turn-in/out.

Route-overlap adjacency

The first adjacency tried was distance-kernel exp(-d/120). It made the graph features worse than no graph at every horizon: a block's neighbours in Euclidean distance are not the blocks whose traffic drives past it. The adjacency the model uses is built from the actual routes:

W[i, j] = (1/Q) · #{ cranes c : shortest path c → block_j passes within 100 m of block_i }
W[i, Q+c] = (1/n_blocks) · #{ blocks j : route c → j passes block_i }

so P·inbound at block i is literally the number of loaded AGVs about to drive past it. Blocks are nodes 0..31, cranes 32..37.

4. Discrete-event model

terminal/des.py is a heap of (time, seq, event) in seconds. SimPy would be shorter; the heap is there so the sim runs with nothing but the standard library and numpy on the terminal's air-gapped box.

ProcessRule
vesselArrives at ETA. Two berths, three cranes each. Both taken → anchor queue; 30 min berth shift when one frees.
craneLands a box on the hook 110 s after the previous one was taken. Cannot start the next cycle until an AGV takes this one: a missing AGV stalls the crane, and stall seconds are the primary KPI.
AGVAssigned to (box, block). Drives empty to the crane, waits for the hook if early, loads, drives to the block (+25 s unload), frees, triggers dispatch.
blockStacks until 320. Each box leaves via the gate after its dwell, drawn log-normal from the line's dwell profile.
policydispatch(T) is called on every new-box and free-AGV event. It sees free AGVs, the crane queues, occupancy and in-flight boxes.

A bug worth recording

The first version scheduled the next crane cycle CYCLE_S after the AGV pickup and stamped the next box ready at born + CYCLE_S: the crane cycle was effectively doubled, throughput was ~85 moves/h and both policies looked identical because nothing downstream of the hook mattered. Fixing it was what made the policy comparison meaningful.

5. Assignment engine

Baseline: greedy

First waiting box, nearest free AGV, nearest block with room. It is what most terminals run, and it is hard to beat on crane stall because it never spends travel on anything else.

Matrix

Every dispatch call solves one rectangular assignment over all free AGVs and all waiting boxes with scipy.optimize.linear_sum_assignment:

cost[a, b] = max(travel(a → crane_b) − ready_in_b, 0) + 0.1 · travel(a → crane_b)

Lateness against the hook is what stalls a crane, so lateness is the cost; the small travel term breaks ties toward short empty runs. The block leg is deliberately not in the pairing cost: it belongs to the box, not to which AGV carries it. Including it was the first version's mistake and cost 30+ minutes of stall per crane.

Block choice

cost[k] = leg_k + slack · ( 60·|depth_k − want_deep| + 25·congest_k ) + 250·fill_k³
want_deep = clip(dwell_days / 6, 0, 1)    slack = clip((free_AGVs − waiting_boxes) / (0.3·fleet), 0, 1)

depth is normalised gate distance, congest is the model's predicted AGV density around the block over the next 15 min, fill includes in-flight boxes. slack is the key control: when AGVs are to spare the policy spends travel on yard shape (long stayers deep, short stayers gate-side, avoid predicted traffic); when cranes are starving, the shortest leg wins and only saturation still matters.

6. Spatio-temporal traffic model

DCRNN-style diffusion convolution with a gradient-boosting readout instead of a recurrent cell. P = D⁻¹W on the route graph; per-node features X = [occ/320, inbound, crane queue, density, sin(hour)]; hops [X, PX, P²X] concatenated over 6 lags of 5-minute snapshots. Readout is LightGBM if installed, sklearn HistGradientBoosting otherwise. No learned message-passing weights, so the model refits between shifts in seconds.

Target

Busy AGVs within 150 m of each block, averaged over the next 15 / 30 / 60 minutes. Arrivals-per-block was tried first and the graph could not help with it: arrivals are decided by the policy, not by neighbours. Lane density is physically propagated along routes, which is what the diffusion operator encodes.

Result (48 h, greedy run, 70/30 time split)

K=2 beats K=0 by ~10% at 15 min, the horizon the dispatcher uses; at 30 and 60 min the crane schedule dominates and K=0 is better. Both beat persistence by more than 2×. The live scorer uses K=2 at 15 min only, and the docs report all three so the crossover is visible.

7. Hierarchical forecast & MinT reconciliation

Weekly TEU for three years across terminal → 6 lines → 14 services. Base forecasts are Holt-Winters (multiplicative seasonality, period 52) fitted at every node independently; the point is that they do not add up. On the 8-week holdout the base total and the sum of base services disagree by roughly 180 boxes/week.

ỹ = S · G · ŷ,   G = (Sᵀ W⁻¹ S)⁻¹ Sᵀ W⁻¹,   W = λ·diag(Σ̂) + (1−λ)·Σ̂, λ = 0.5

where S is the summing matrix (21 × 14) and Σ̂ is the covariance of in-sample residuals after the first season. MinT-shrink keeps the total roughly as accurate and improves line and service MAPE by a few tenths of a point, while making the numbers coherent, which is what the yard plan needs: the block plan is built from the bottom and the labour plan from the top.

8. Dwell shrinkage

Dwell per line is log-normal with σ = 0.45. A line with 40 sampled boxes in a 48 h window gets a noisy mean, so the estimate is shrunk toward the terminal prior:

μ_post = ( μ₀/τ² + Σ log xᵢ / σ² ) / ( 1/τ² + n/σ² ),   τ = 0.3
P(dwell > 5 d) = 1 − Φ((ln 5 − μ_post)/σ)

The policy uses exp(μ_post) as the box's expected dwell for depth targeting; the API's yard-plan endpoint uses P(>5 d) > 0.3 to route a booking deep or gate-side.

9. Ingestion & event store

Multi-scale: seconds (lift, stall, berth events), 5 minutes (state snapshots with every AGV's position, block occupancy, crane queues), weeks (volume history). All three land in one store, api/store.py, DuckDB when installed and SQLite otherwise, with the same two tables:

events(run TEXT, t INTEGER, kind TEXT, payload JSON)
snapshots(run TEXT, t INTEGER, payload JSON)

In production the lift and stall events are the TOS's crane PLC messages; snapshots come from the AGV fleet manager's position feed. The Flink-style replay in the dashboard is the WebSocket endpoint reading these tables in time order.

11. Benchmark method

Same layout, same 48 h vessel schedule (deep copy), same fleet, same DES seed. Only the policy changes. The greedy run is also the training data for the traffic model, so the Matrix run is genuinely out-of-sample for the model.

KPIDefinition
moves/hBoxes landed in a block per simulated hour
crane stallMinutes per crane the hook waited with a box for an AGV
AGV empty shareEmpty metres / (empty + loaded metres)
yard peak saturationMax block occupancy / 320 over all snapshots
turnaroundVessel arrival to last crane finished, hours

Honest reading of the result: Matrix matches greedy on throughput and turnaround, cuts empty travel by ~5 points and holds peak block saturation around 60% where greedy fills blocks to 100%. It pays with a couple of minutes more crane stall per crane over 48 h, which is the travel it spends on yard shape. The saturation number is the one that matters operationally: a full block means reshuffles, and reshuffles are not in this model.

12. Drift & what breaks

  • Schedule drift. The traffic model is fitted on one 48 h greedy run. A different vessel mix shifts the density distribution; the fix is what Congestion.fit already is, a between-shift refit from the last day of snapshots.
  • Policy feedback. The model is trained on greedy traffic and used inside Matrix, which changes traffic. Expect the 15 min MAE to degrade in the loop; monitor it from the Matrix run's own snapshots and refit on those once enough exist.
  • Layout changes. Any block closure changes route_adjacency. Rebuild P; the readout can stay.
  • Reshuffles. Not modelled. Saturation above ~85% in reality triggers rehandles that cost crane time; the model treats it as a soft penalty only.
  • Seasonality break. Holt-Winters with a 52-week period assumes the pattern repeats. A new service or a lost contract shows up as a persistent residual on one bottom series; MinT will spread that error to its siblings, so watch per-series residuals, not the reconciled total.
